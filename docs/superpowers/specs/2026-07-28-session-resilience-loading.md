# Session 韌性與載入指示

- 日期：2026-07-28
- 狀態：ready-for-agent
- 範圍：`web/`（前端），後端不動

## Problem Statement

使用者在實際操作網站時遇到兩個讓人以為「網站當掉」的問題：

1. **請求進行中沒有任何指示。** 點進庫存、品類、設定頁時，資料回來之前畫面是空的；按下「儲存」「擷取」之後按鈕沒有任何變化，使用者無從判斷是系統在忙、還是自己沒點到，於是重複點擊。
2. **閒置一陣子後整站失效，但畫面留在原地。** 使用者離開一段時間再回來操作，畫面不會導向登入頁，只跳出一個紅色錯誤 toast，之後所有操作都失敗，必須自己手動重新整理才知道要重新登入。

第二點的表象是「token 過期沒處理」，但實際根因不是 token 壽命，也不是缺少 silent refresh。系統**已經**具備 401 自動換發並重送原請求的機制。真正的缺陷是：

- **Refresh token rotation 遇上並行請求會互相打死。** 後端的 refresh 流程會作廢舊 refresh token 並發新的（token rotation）。前端多數頁面在初始化時同時發出 2–3 個請求（庫存頁：品類清單、標籤清單、搜尋；設定頁：外部帳號、同步任務、分享連結；品項編輯頁：品類清單、品項內容）。access token 過期後首次進入任一頁面，這些請求會同時收到 401，各自觸發一次換發，後端只認第一個，其餘拿著已作廢的 token 得到 403。前端把 403 當成「連 refresh token 都過期了」而清空 session，連同第一個請求剛換好的有效 session 一起清掉。
- **清空 session 之後不做任何導航。** 登出動作只清掉記憶體狀態與 localStorage，路由守衛不會重跑，畫面上的元件繼續存活並繼續發請求。這同一個缺陷也讓 header 的「登出」按鈕壞掉：按下去只有 header 消失，底下的頁面還活著。

## Solution

**Session 韌性**

- 換發動作全域去重：同一時間內只會有一次換發在飛，並行的 401 全部共用同一次結果。使用者感受不到 access token 過期。
- 清空 session 時一併導向登入頁。因 session 過期被踢出時帶上原本的位置，重新登入後回到原頁；使用者主動按登出則不帶，單純回到登入頁。
- Access token 壽命維持不變。

**載入指示**

- 全站頂部一條 indeterminate 進度條，由 HTTP 層的 in-flight 計數驅動，涵蓋所有頁面的讀取，不需要每個頁面各自實作。短請求不觸發顯示，避免閃爍反而更像故障。
- 所有改寫性操作（建立、更新、刪除、外部擷取、同步）的按鈕在請求進行中顯示忙碌文字並停用。這同時解決重複送出造成重複建檔的正確性問題。

## User Stories

### Session 韌性

1. 作為已登入的使用者，我希望離開電腦一小時後回來點任何頁面時系統自動續期，這樣我不會因為背景的 token 過期而被打斷。
2. 作為已登入的使用者，我希望一個頁面同時發出的多個請求在 token 過期時只觸發一次續期，這樣不會因為彼此搶著續期而把我的登入狀態弄壞。
3. 作為已登入的使用者，我希望續期成功後原本的每一個請求都自動重送並拿到資料，這樣我看到的是完整的頁面而不是半頁資料。
4. 作為登入狀態真的已經失效的使用者，我希望系統直接把我帶到登入頁，這樣我立刻知道要重新登入，而不是面對一個每按一下就跳錯誤的殭屍畫面。
5. 作為因 session 過期被導向登入頁的使用者，我希望重新登入後回到我原本正在看的頁面，這樣我不用重新找一次路。
6. 作為主動按下登出的使用者，我希望立刻被帶到登入頁，這樣我確認自己真的登出了。
7. 作為主動按下登出的使用者，我希望重新登入後停在首頁而不是回到我登出前的頁面，這樣登出的語意是乾淨的。
8. 作為在共用電腦上使用的使用者，我希望登出後原本頁面上的元件不再繼續發送請求，這樣不會有殘留的資料留在畫面上。
9. 作為使用者，我希望背景續期失敗時看到的訊息是「請重新登入」這種可行動的指引，而不是後端的技術性錯誤字串。
10. 作為使用者，我希望我的登入狀態能維持數天，這樣日常使用不需要頻繁輸入密碼。

### 載入指示

11. 作為進入庫存頁的使用者，我希望在清單載入期間看到明確的進行中指示，這樣我知道系統在工作而不是壞了。
12. 作為進入品類頁的使用者，我希望看到同樣的進行中指示，這樣不同頁面的等待體驗是一致的。
13. 作為進入設定頁的使用者，我希望看到同樣的進行中指示，即使該頁同時在載入三種不同資料。
14. 作為開啟既有品項編輯頁的使用者，我希望在品項內容載入期間看到進行中指示，這樣我不會以為表單是空的。
15. 作為使用者，我希望很快就回來的請求不要閃出一下進度條，這樣畫面不會有惱人的閃爍。
16. 作為使用者，我希望進度條固定在畫面頂部而不遮蔽內容，這樣我在等待期間仍能閱讀已載入的部分。
17. 作為使用者，我希望進度條在請求失敗時也會消失，這樣不會有一條永遠跑不完的進度條留在畫面上。
18. 作為使用者，我希望多個請求重疊時只看到一條進度條，並在最後一個請求結束時才消失。
19. 作為使用螢幕閱讀器的使用者，我希望載入狀態有適當的無障礙標示，這樣我也能得知系統正在忙碌。

### 防止重複送出

20. 作為新增品項的使用者，我希望按下儲存後按鈕立刻停用並顯示「儲存中…」，這樣我不會因為連點而建立出多筆重複品項。
21. 作為編輯品項的使用者，我希望儲存期間按鈕停用，這樣不會送出多次互相覆蓋的更新。
22. 作為刪除品項的使用者，我希望刪除期間按鈕停用，這樣不會對同一筆資料送出多次刪除。
23. 作為使用商品網址自動填表的使用者，我希望擷取期間按鈕顯示「擷取中…」並停用，這樣我知道系統正在抓取遠端網頁（這是最慢的操作之一）。
24. 作為擷取商品網址的使用者，我希望擷取失敗後按鈕恢復可用，這樣我可以換一個網址再試。
25. 作為在設定頁綁定外部帳號的使用者，我希望綁定期間按鈕停用，這樣不會送出重複的綁定請求。
26. 作為在設定頁觸發同步的使用者，我希望同步請求送出期間按鈕停用，這樣不會建立多個重複的同步任務。
27. 作為在設定頁建立分享連結的使用者，我希望建立期間按鈕停用，這樣不會產生多條非預期的公開連結。
28. 作為編輯品類的使用者，我希望儲存期間按鈕停用，這樣 schema 不會被重複送出的請求弄亂。
29. 作為使用者，我希望改寫操作失敗後按鈕恢復可用，這樣我修正輸入後可以重試。
30. 作為使用者，我希望純讀取的操作（搜尋、篩選、換頁）不要停用按鈕，只靠頂部進度條表達忙碌，這樣操作手感不會變遲鈍。

## Implementation Decisions

### 前端 Session

- **換發去重放在前端的 auth 服務層，不改後端。** 換發方法內部持有一個「進行中」的 promise 快取，第一個呼叫者建立、後續呼叫者共用，完成（無論成敗）後清空快取。這是最小改動、且不削弱 refresh token rotation 的安全性。
  - 明確否決的替代方案：後端取消 rotation（失去 token 外洩偵測能力）、後端為舊 token 加寬限期（需在使用者文件多存一組前一版雜湊與其到期時間，複雜度最高）。
- **導向登入頁的責任歸屬於 auth 服務的登出方法**，而非攔截器或根元件。登出方法接受一個選用的 returnUrl 參數：有值時導向登入頁並帶上該查詢參數，無值時單純導向登入頁。這樣一處修正同時涵蓋「session 過期」與「使用者主動登出」兩條路徑，避免兩地重複。
  - 路由守衛已經在未登入時產生帶 returnUrl 的登入頁 UrlTree，登入頁對該參數的既有處理不變。
- **攔截器在換發失敗時呼叫登出並帶入當前路由位置。** 換發端點失敗時後端回的是 403（不是 401），前端不依賴狀態碼，只依賴「換發這個動作失敗了」這件事。
- **Access token 與 refresh token 壽命維持現值不變（30 分 / 14 天）。** 一旦去重生效，access token 過期對使用者不可見，延長只會拉長撤銷視窗而換不到體驗改善。原提案的「延長至 2 小時」經評估後放棄。
- **不儲存 access token 的到期時間，不做到期前主動換發。** 後端回應中的到期時間欄位維持現狀被忽略。反應式換發（401 觸發）在去重之後已足夠。

### 載入指示

- **新增一個載入狀態服務**，維護 in-flight 請求計數，對外暴露一個布林訊號。計數必須在成功與失敗兩條路徑上都正確歸零。
- **新增一個 HTTP 攔截器**，在請求開始時遞增、結束時遞減。**不排除任何端點**，包含背景的換發請求 —— 建立例外清單只會製造計數漏歸零的風險。
- **延遲顯示。** 忙碌狀態持續超過門檻（200 毫秒）才顯示進度條，短請求完全不觸發。門檻邏輯歸屬於載入狀態服務或根元件，不散落到各頁面。
- **進度條由根元件渲染**，固定於 header 下緣，indeterminate 動畫，沿用既有的霓虹設計語彙與 CSS 變數。需附無障礙標示（`role="progressbar"` 或等效的 aria-live 區域）。
- **攔截器註冊順序**：載入攔截器需涵蓋認證攔截器所觸發的重送，註冊順序以此為準。

### 防止重複送出

- **僅改寫性操作（POST / PUT / DELETE）加按鈕級忙碌狀態**，讀取交由全局進度條表達。涵蓋：品項編輯頁的儲存 / 刪除 / 網址擷取、設定頁的綁定 / 解除綁定 / 觸發同步 / 建立分享、品類頁的儲存。
- **忙碌狀態以各元件本地訊號表示**，沿用專案既有 pattern（登入頁的送出按鈕、圖片上傳元件皆為此形式），不引入新抽象。
- **忙碌時按鈕同時 disabled 並改變文字**（例：「儲存」→「儲存中…」），與登入頁一致。
- **錯誤路徑必須解除忙碌狀態。** 現有多處 subscribe 只提供 next 回呼，需補上 error 回呼或等效機制。
- 既有的儲存按鈕停用條件（表單有效性）與忙碌條件為 OR 關係，不取代原有驗證。

### 不涉及的變更

- 後端零改動：`RefreshCommandHandler` 的 rotation 邏輯、`JwtOptions` 的壽命設定、任何端點契約皆不變。
- 資料庫 schema 不變。

## Testing Decisions

**好的測試在此專案的定義**：只驗外部可觀察的行為 —— 送出了幾個 HTTP 請求、導向了哪個路由、按鈕的 disabled 屬性與文字。不驗私有欄位、不驗服務內部的 promise 快取是否存在、不驗計數器的瞬時數值。判準是：若把實作換成另一種等效寫法（例如用 RxJS `shareReplay` 取代 promise 快取），測試應該仍然通過；若行為退化（並行時打了兩次換發），測試應該失敗。

**Seam 選擇**：不新增 seam，全部使用既有的兩個。

1. **HTTP 攔截器鏈 seam（首選，涵蓋大部分行為）** —— 以 `provideHttpClient(withInterceptors([...]))` 搭配 `provideHttpClientTesting` 組出真實的攔截器鏈，注入真實的 auth 服務，用 `HttpTestingController` 精確斷言送出的請求數與內容。這是最高、最穩定的 seam：不掛載任何元件，卻能驗到跨請求的併發語意。
   - 先前技術：`web/src/app/core/auth.interceptor.spec.ts` 已建立此模式，並已備有等待 promise 鏈與 microtask 排空的輔助手法（既有註解說明為何使用 macrotask）。

2. **元件 seam（僅用於 UI 狀態）** —— `TestBed` 掛載獨立元件，以 stub 服務（回傳 `of(...)`）取代 API 服務，斷言渲染後的按鈕屬性與文字。
   - 先前技術：7 個既有的 `*.component.spec.ts` 皆為此形式，其中 `item-detail.component.spec.ts` 已示範完整的 stub 組合（`CategoryService` / `CatalogService` / `IngestionService` / `NotificationService` / `ActivatedRoute` / `provideRouter`）。

**待測行為清單**

於攔截器鏈 seam：

- 兩個並行請求同時收到 401 時，只有一個換發請求被送出。
- 上述情境下兩個原始請求都以新 token 重送並成功回傳。
- 換發請求本身失敗時，session 被清空且路由導向登入頁（以 `Router` spy 斷言導航目標與 returnUrl 查詢參數）。
- 換發成功後，後續的新請求直接帶新 token，不再觸發換發。
- 載入計數在請求成功後歸零。
- 載入計數在請求失敗後同樣歸零（這是最容易寫錯、且失敗徵狀為「進度條永遠不消失」的路徑）。

於元件 seam：

- 品項編輯頁：儲存請求進行中時儲存按鈕為 disabled 且文字為忙碌態；請求完成後恢復。
- 品項編輯頁：擷取請求失敗後按鈕恢復可用。
- 設定頁：同步按鈕在請求進行中為 disabled。

**明確不寫的測試**：進度條的 200 毫秒延遲門檻（時間相依、脆弱，改以人工確認）、進度條的視覺樣式。

## Out of Scope

- 後端任何變更，包含 refresh token rotation 策略、token 壽命設定、寬限期機制。
- 到期前主動換發（pre-emptive refresh）與相應的到期時間狀態管理。
- Skeleton loader 或各頁面客製的載入版面；本次僅提供全局進度條。
- 讀取類操作（搜尋、篩選、載入更多）的按鈕級忙碌狀態。
- 精選頁既有的頁面級 loading 訊號與圖片上傳元件既有的忙碌狀態，維持原樣不重構。
- Toast 通知機制的任何調整。
- 跨瀏覽器分頁的 session 同步（多分頁同時觸發換發的情境）。
- 從商品網址自動填表功能本身已知的其他缺口（擷取到的圖片與屬性未被使用、後端未防範 SSRF），另案處理。

## Further Notes

- **交付方式**：自 `master` 開一支分支，兩個 commit —— `fix(web):` 涵蓋 session 韌性，`feat(web):` 涵蓋載入指示與防重複送出。兩者可獨立回滾。
- **工作目錄雜訊**：`web/angular.json` 目前有一筆 Angular CLI 自動加入的 analytics ID 變更，與本案無關，不納入 commit。
- **手動驗證建議**：暫時把後端的 access token 壽命設為 1 分鐘，登入後停留一分鐘再點進庫存頁，確認畫面不跳錯誤、資料正常載入、且瀏覽器 Network 面板只出現一次 `/auth/refresh`。驗證完務必還原設定。
- **跨分頁情境的已知限制**：本次的去重是單一分頁內的記憶體狀態。兩個分頁同時觸發換發仍會有一方被 rotation 打死並被導向登入頁。單人使用的收藏管理站可接受，若日後成為困擾，再考慮 BroadcastChannel 或後端寬限期。
- 本文件的結論來自 2026-07-28 的一次 grilling 討論，其中修正了「系統沒有 silent refresh」與「問題出在 token 壽命太短」這兩個初始假設。
