# Steam 繁體中文遊戲中繼資料

## Problem Statement

使用者的收藏清單裡，從 Steam 同步回來的遊戲全部是英文品名，經 IGDB 補完的簡介與類型也是英文。

對一位以繁體中文為母語的收藏者來說，這造成三個實際困擾：

1. **認不出來**——他熟悉的是「艾爾登法環」「黑神話：悟空」，不是 `ELDEN RING`、`Black Myth: Wukong`。清單裡幾百款英文標題，掃視時要逐一翻譯回中文才知道那是哪款遊戲。
2. **搜尋不到**——他在搜尋框輸入「巫師」，找不到 `The Witcher 3: Wild Hunt`。系統的搜尋是對存下來的字串做比對，存的是英文就只搜得到英文。
3. **分類看不懂**——類型欄位寫著 `Action, RPG` 而不是「動作、角色扮演」，與整個介面的繁體中文格格不入。

使用者可以手動把每一筆改成中文，但一來數量太多，二來目前每次同步都會把手改的品名蓋回英文，改了也留不住。

## Solution

系統多一條**本地化補完**路徑：向 Steam 商店索取繁體中文版的品名、簡介與類型，覆寫既有的英文內容。

從使用者的角度：

- 設定頁多一顆「補完繁體中文資料」按鈕。按下去之後作業在背景進行，使用者可以離開頁面，隨時回來看作業紀錄的進度。
- 補完完成後，清單裡的遊戲顯示繁體中文品名，簡介與類型也是中文。
- 沒有官方繁中版的遊戲維持原文（例如 `Cyberpunk 2077`）——這是 Steam 官方的資料現況，不是系統失敗，也不會顯示錯誤。
- 單一品項的詳細頁可以單獨重新抓取，作為改壞了之後的修正出口。
- 之後每次同步不會再把品名改回英文。

一併解決的既有問題：使用者手動改過的品名，現在會在下一次同步被默默蓋掉；本次調整後同步不再擁有品名，手改的內容得以保留。

## User Stories

1. 作為收藏者，我想看到遊戲的繁體中文品名，這樣我掃視清單時能立刻認出每一款遊戲。
2. 作為收藏者，我想用中文關鍵字搜尋我的遊戲，這樣我不必先把中文譯回英文才找得到。
3. 作為收藏者，我想看到繁體中文的遊戲簡介，這樣我不必為了想起「這款在講什麼」而閱讀英文。
4. 作為收藏者，我想看到繁體中文的遊戲類型，這樣類型欄位與介面其他部分語言一致。
5. 作為收藏者，我想在設定頁用一顆按鈕觸發整批補完，這樣我不必逐筆處理幾百款遊戲。
6. 作為收藏者，我想在補完進行時離開頁面去做別的事，這樣長時間的作業不會綁住我的瀏覽器。
7. 作為收藏者，我想從作業紀錄看到補完的進度與結果，這樣我知道它還在跑、跑完了、或是失敗了。
8. 作為收藏者，我想讓沒有官方繁中版的遊戲安靜地保持原文，這樣我不會被一堆「查無資料」的錯誤淹沒。
9. 作為收藏者，我想在單一品項的詳細頁重新抓取該筆資料，這樣我能修正個別抓錯或想更新的品項。
10. 作為收藏者，我想讓我手動改過的品名在同步後留存，這樣我的編輯不會被系統默默還原。
11. 作為收藏者，我想讓我自己寫的心得不被 IGDB 的英文簡介蓋掉，這樣我的內容優先於外部資料。
12. 作為收藏者，我想在補完一次之後，之後的整批補完自動跳過已處理的品項，這樣重跑不會浪費時間重抓。
13. 作為收藏者，我想讓新買的遊戲在下次整批補完時也拿到繁中資料，這樣這個功能不是一次性的。
14. 作為收藏者，我想讓實體遊戲品項（非 Steam 同步而來）在系統查得到對應 Steam 遊戲時也能拿到繁中資料，這樣我的實體收藏不會被排除在外。
15. 作為收藏者，我想在品項詳細頁看到該遊戲的 Steam App ID，這樣我能自己去商店頁對照。
16. 作為收藏者，我想手動填入 Steam App ID 來讓一筆手動建檔的品項能被補完，這樣我有辦法把系統認不出來的品項接上。
17. 作為收藏者，我想讓補完不建立新品項，這樣我的清單不會因為補完而多出我沒有的遊戲。
18. 作為收藏者，我想讓補完只影響我自己的收藏，這樣不會動到其他使用者的資料。
19. 作為收藏者，我想在 Steam 商店暫時無法連線時，補完把該筆記為失敗而不是中斷整個作業，這樣其餘品項仍會完成。
20. 作為收藏者，我想讓補完的速度受控而不被 Steam 封鎖，這樣我不會因為跑一次補完就短時間內無法使用任何 Steam 功能。
21. 作為收藏者，我想讓類型欄位在補完後只有一種語言，這樣不會今天中文明天英文地跳動。
22. 作為收藏者，我想讓沒有繁中資料的品項保留 IGDB 提供的英文類型而不是變成空白，這樣資訊只會增加不會減少。
23. 作為收藏者，我想讓補完不動我的標籤、展示設定、入手資訊與圖片，這樣它只補中繼資料不碰我的整理成果。
24. 作為系統維運者，我想在設定檔調整目標語言與國別，這樣未來要換成日文或簡體中文不必改程式碼。
25. 作為系統維運者，我想讓 Steam 商店的請求間隔可設定，這樣 Steam 調整限制時我能跟著調。
26. 作為系統維運者，我想讓補完的失敗被記錄下來並歸屬到正確的來源，這樣排查時我找得到是哪個外部服務出問題。
27. 作為開發者，我想讓「可搜尋」與「可依識別碼反查」是兩種能力，這樣只支援其中一種的來源不必實作用不到的空樁。
28. 作為開發者，我想讓每個來源自行宣告哪些欄位是覆蓋、哪些是讓位，這樣多個來源寫同一個欄位時結果與執行順序無關。
29. 作為開發者，我想讓「這筆補完過了」與「這筆的外部識別碼」是兩個獨立概念，這樣一個來源寫入識別碼不會誤判成另一個來源已完成工作。
30. 作為開發者，我想讓 Steam 相關程式不依賴 IGDB 是否啟用，這樣沒有設定 IGDB 憑證的部署仍能正常同步與補完。
31. 作為前端開發者，我想讓補完的入口元件吃來源代號而非綁死單一來源，這樣新增第三個來源時不必再複製一份。
32. 作為收藏者，我想讓自訂品類也能加上 Steam 補完所需的欄位，這樣我不必只能用系統內建的遊戲品類。

## Implementation Decisions

### 詞彙

沿用並擴充既有語彙（詳見 `CONTEXT.md`）：

- **同步（Sync）**——以已綁定帳號整批拉回品項，會建立品項。
- **補完（Enrich）**——對既有品項補欄位，絕不建立品項。
- **本地化補完**——本次新增的補完路徑，向 Steam 商店取得繁體中文品名、簡介、類型。
- **欄位擁有權**——某來源對某欄位是「無條件覆蓋」還是「僅在品項尚無值時寫入」（軟寫入）。
- **完成標記**——整批補完用來排除已處理品項的欄位。
- **外部識別碼來源**——用來組出外部識別碼字串的欄位。

### 資料來源

繁體中文資料取自 Steam 商店的 app 詳細資料端點，帶語言與國別參數。這是一支**無官方文件、無 SLA 的端點**，但它是唯一同時提供繁中品名、簡介與類型的來源。已驗證的行為：

- 有官方繁中版的遊戲回傳中文品名；沒有的自動回傳原文，不需要在我們這端寫退回邏輯。
- 類型一律本地化。
- 一次只能查一個 app；帶多個識別碼會回傳空值，因此無法批次。
- 速率上限約每五分鐘兩百次請求。

IGDB 的 `game_localizations` 被評估後否決：它只提供品名不提供簡介，且與下述的品名擁有權模型衝突。

不從這支端點取用的欄位：開發商、發行商（仍是英文原名）、發售日期（本地化字串無法穩定解析）、平台（結構與現有欄位不符）。這些維持由 IGDB 提供。

### 來源能力介面

`ISearchProvider` 拆成兩層：

- **可依識別碼反查**——提供外部識別碼來源欄位、完成標記欄位、必要品類欄位，以及批次反查方法。補完只需要這一層。
- **可搜尋**——繼承上一層，另加關鍵字搜尋。

Steam 來源實作前者但不實作後者，因此不必寫用不到的搜尋空樁。能力旗標新增一個「可補完」成員，由實作的介面推導，前端據此決定是否顯示入口。

Steam 來源同時具備「整批同步」與「可依識別碼反查」兩種能力，仍是同一個來源代號——這讓外部識別碼在兩條路徑上都是同一種字串，補完端點也自然指向 Steam 同步而來的品項。

### 外部識別碼來源與完成標記分離

兩者刻意是不同欄位：

- **外部識別碼來源** = Steam App ID。IGDB 補完在反查得到時也會寫入這個欄位，讓非 Steam 同步而來的品項（例如實體遊戲）也能被本地化補完定址到。
- **完成標記** = Steam 資料更新時間，只有本地化補完自己會寫。

合成一個欄位的話，IGDB 一旦寫入 App ID 就等同宣告本地化補完已完成，該品項會被整批補完永久跳過。

### 欄位擁有權

每個來源在回傳結果時宣告哪些欄位是軟寫入；未宣告者一律覆蓋。品名與簡介雖非屬性欄位，走同一套規則，不再各自寫一段條件判斷。

- **本地化補完**：品名、簡介、類型全部覆蓋。
- **IGDB 補完**：簡介、類型、Steam App ID 為軟寫入；其餘（開發商、發行商、發售日期、評分、封面）維持覆蓋。

結果與執行順序無關：本地化補完先跑則 IGDB 讓位，IGDB 先跑則本地化補完覆蓋。

已知代價：使用者在首次補完之前手動改過的品名或簡介會被覆蓋。單筆重新抓取是使用者主動修正的出口。

### 品名的擁有權從同步移到補完

同步只拿得到英文品名，因此同步不再於既有品項上更新品名，僅在建立品項時寫入。品名的更新交給補完。

- 代價一：Steam 端真正的更名（例如搶先體驗轉正式版改名）不再傳播進來。
- 代價二（正面）：使用者手動改過的品名不再被同步蓋掉。

補完的寫入契約隨之放寬為可寫品名；標籤、展示狀態、入手資訊、圖片、建立時間、來源仍一律不碰，且永不建立品項。

### 執行方式

本地化補完改走背景佇列，沿用專案既有的背景服務模式。補完端點立即回應一筆進行中的作業，前端輪詢作業清單取得進度。

理由：以受控間隔逐款請求，數百款遊戲需時數分鐘至十數分鐘，遠超過 HTTP 請求的合理生命週期。

**已知不一致**：補完端點因此有兩種語意——IGDB 在回應時已完成，Steam 在回應時才剛開始。列為待清理，本次不統一。

### 設定

目標語言、國別、商店主機位址、請求最小間隔都放進 Steam 的設定區段，預設值即繁體中文與台灣。商店與 Web API 不同源，因此是第二個具名 HTTP 用戶端，並有自己的節流器。

節流的機制抽成共用元件，由 IGDB 與 Steam 商店各自綁定自己的間隔設定，兩者互不拖累。

### 品類欄位

系統的實體遊戲與數位遊戲品類新增 Steam App ID 與 Steam 資料更新時間兩個欄位。類型欄位兩個品類本來就有，沿用不另立。

自訂品類可透過既有的「補上來源必要欄位」端點加入這些欄位——該端點的來源解析放寬到「可依識別碼反查」層級，因此 Steam 也適用。

### 前端

補完入口元件從綁死 IGDB 泛化為吃來源代號，設定頁與品項詳細頁各自呈現兩個來源的入口。既有的 IGDB 元件與其測試一併重構，不複製第二份。

## Testing Decisions

好的測試只驗證外部可觀察的行為：資料庫裡最後是什麼、API 回應是什麼、畫面上出現什麼。不驗證某個方法被呼叫幾次、內部欄位叫什麼名字。測試必須在商業邏輯改變時失敗，而不只是在重構時失敗。

### 主接縫——補完作業執行器

位於 HTTP 之下、外部來源之上，是「工作仍為同步、結果可直接觀察」的最高點。以真實 Mongo 搭配既有的 HTTP 樁與回應樣本驅動，涵蓋：

- 有繁中版的遊戲，品名、簡介、類型在資料庫裡變成中文。
- 沒有繁中版的遊戲維持原文，且不算失敗——**這一案必須存在**，它是「不需要自寫退回邏輯」這個決定的證據。
- 欄位擁有權：IGDB 不覆蓋既有類型與簡介，本地化補完會覆蓋。
- 品名寫入生效。
- 完成標記存在的品項不出現在整批候選；只有識別碼而無完成標記的品項會出現。
- 非 Steam 同步而來但已有 Steam App ID 的品項能被定址到。
- 外部服務失敗時該筆記為失敗，其餘品項仍完成。

既有的 IGDB 來源測試與 Mongo 補完寫入測試是這類測試的既有範例。

### 次接縫——前端元件測試

不同 runtime，無法併入主接縫。驗證泛化後的補完元件對不同來源代號呈現正確入口、進行中停用按鈕、詳細頁的兩顆重新抓取按鈕。

### 補完指令單元測試（既有接縫，擴充）

以假造的來源驅動補完指令，直接釘住欄位擁有權的判斷邏輯——軟寫入在有值時讓位、無值時寫入、未宣告者一律覆蓋。這層與主接縫有部分重疊，但它讓擁有權規則的意圖在不依賴任何外部回應樣本的情況下被明確表達。專案既有的補完指令測試就是這個接縫。

### 兩個薄測試（掛在既有接縫）

- 補完端點對 Steam 來源回應一筆進行中的作業。
- **同步重跑不覆蓋既有品名**——釘住品名擁有權的移轉。這是最難以察覺的回歸：若有人把它改回去，繁中品名會在下一次同步被默默改回英文，而沒有任何錯誤訊息。

### 刻意不做

不另外撰寫獨立的資料映射單元測試——其行為完全被主接縫涵蓋，多一層只是重複覆蓋。

## Out of Scope

- **未在 Steam 上架的遊戲**——實體獨佔、絕版、非 Steam 平台的遊戲取不到繁中資料，維持原文。
- **開發商、發行商、發售日期、平台的本地化**——公司名稱通常不翻譯，日期與平台語言中性。
- **每位使用者各自選擇語言**——品名只有一個欄位，存不下多語言；做了只會變成使用者互相覆蓋彼此的資料。同時保留原文與譯名（雙欄位）一併排除，那會讓清單、搜尋、排序、匯出、分享頁全都要各自決定用哪一個。
- **統一補完端點的同步／非同步語意**——已記為待清理。
- **本地化補完路徑的使用者編輯保護**——本次刻意讓位給「資料一致變成繁中」的目標，單筆重新抓取是修正出口。
- **IGDB 的繁中品名來源**——與品名擁有權模型衝突，已否決。

## Further Notes

- 對 Steam 商店端點的所有行為描述（品名退回原文、類型一律本地化、不可批次、速率上限）都是實測結果，不是文件推測——該端點沒有官方文件。Valve 若變更行為，主接縫的「退回原文」與「有繁中版」兩案會是第一個發出訊號的地方。
- 本文件記錄的十二項決定中，有三項符合「難以逆轉、缺少脈絡會困惑、來自真實取捨」而值得寫成 ADR：品名擁有權由同步移轉至補完、採用無官方文件的商店端點、本地化補完非同步而 IGDB 補完同步。
- 使用者的原始描述是「從 Steam/IGDB 同步的資料是英文」，但英文品名來自**同步**、英文簡介與類型來自**補完**，兩者是不同路徑。繁中品名並非透過修改同步取得，而是由一條新的補完路徑覆蓋同步寫入的英文——這是整個設計的軸心。
