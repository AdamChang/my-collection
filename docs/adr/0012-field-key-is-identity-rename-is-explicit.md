# ADR-0012：欄位鍵是身分，改名是明確操作，不引入 FieldId

- 狀態：已接受
- 日期：2026-09-15
- 相關：[ADR-0006](0006-platform-filter-in-all-view-is-a-hardcoded-whitelist.md)（`platform` 是跨品類的字面白名單）、[ADR-0010](0010-catalog-url-is-truth-return-point-is-memory.md)（`attr.<key>` 進網址）

## 背景

品類的 `fields[]` 是整個系統的 schema：Angular 動態表單、FluentValidation 動態規則、篩選器 UI 都由它驅動。每個欄位只有一個 `Key`，品項的 `attributes` 是以這個 `Key` 為名的 `BsonDocument`。

`UpdateCategoryCommandHandler` 收到的是整份新的 `fields[]`，整包置換舊的；品項一筆都不碰。前端編輯表單對既有欄位的 `Key` 是可自由編輯的輸入框。結果是：使用者把 `price` 改成 `purchasePrice` 之後，schema 只認識新鍵，品項上的值全在舊鍵底下——表單看不到、儲存時被當成未宣告的鍵而擋下（`b9bc142` 之前是 400、之後是靜默濾掉）。從資料上看，「改名」與「刪掉一個欄位、新增另一個欄位」是同一件事，後端沒有任何辦法區分。

2026-08-07 的止血只讓儲存不再失敗；值救不回來，這件事從那天起掛在 Dashboard 的 🔴。

## 決定

### 一、欄位鍵是身分，不是名字

`Key` 建立後就是這個欄位的身分。它不是給人看的——給人看的是 `Label`，可以隨意改。

理由是 `Key` 早已在系統各處被**字面定址**：Mongo 路徑 `attributes.{key}`（篩選、補完寫入、同步寫入、`missingAttrs`）、每個來源的欄位常數（`steamAppId`、`steamStoreUpdatedAt`、`genres`、IGDB 與 PSN 各自的鍵）、ADR-0006 的 `platform` 白名單、ADR-0010 進網址的 `attr.<key>`。一個在這麼多地方被當作身分用的東西，就應該被當作身分對待。

### 二、改名是使用者明確發出的操作，不是系統推斷出來的

新增 `RenameCategoryFieldCommand(categoryId, oldKey, newKey)` 與對應端點。它做三件事，且在同一個 MongoDB transaction 內完成：schema 裡的鍵換掉、該品類下所有品項的 `attributes.oldKey` 搬到 `attributes.newKey`、回報搬了幾筆。

改名**只動鍵**。型別、選項、必填等其他設定走原本的 `PUT`。把型別變更混進來，會把「既有值不符合新型別怎麼辦」這個尚未定義的問題一起帶進 transaction。

`PUT /categories/{id}` 從此的語意是**宣告集合的置換**：請求裡沒有的既有鍵就是撤回宣告，請求裡多出來的鍵就是新增宣告。它不猜「這兩個是不是同一個欄位改了名」——猜對了是運氣，猜錯了是資料損毀。前端對既有欄位的 `Key` 輸入框改為唯讀，旁邊提供「重新命名」動作，按下即送出改名命令，不等表單儲存。

### 三、撤回宣告不刪值

撤回一個欄位的宣告，品項上的值原封不動留著；重新宣告同一個鍵，值就回來。系統不會再寫它、也不會讀出來給表單，但它一直在——`CONTEXT.md` 稱之為**未宣告屬性**。

這是個人收藏工具，誤刪一個欄位的成本遠高於幾個多餘鍵的儲存成本；「重新宣告就回來」是使用者唯一的反悔路。代價是 `AttributeValidator` 的「未經宣告的鍵不允許寫入」只在寫入面成立，儲存層允許未宣告的鍵存在。

這條規則決定了改名的衝突規則：新鍵若已被同品類宣告，拒絕；某些品項若**同時**帶有舊鍵與新鍵（新鍵是未宣告屬性），拒絕並回報品項數——覆蓋等於刪，而我們剛決定不刪；某些品項若只帶新鍵沒有舊鍵，放行，這正是「重新宣告就回來」。

### 四、來源欄位不可改名、不可撤回

由來源要求品類宣告的欄位（`SteamFields` / `IgdbFields` / `PsnFields` 的全部定義）以及 ADR-0006 的 `platform`，一律鎖定。來源用字面值找到這些鍵，改了名補完就寫到宣告之外，錯誤不會在改名當下出現，會在下一次補完時才以「值不見了」的形式出現。

鎖定集合來自**靜態目錄**，不來自 `ProviderRegistry`。registry 只包含這個部署有註冊的來源，而 IGDB 曾因憑證缺失整組不註冊達十八天——那段期間若使用者刪掉 `igdbId`，憑證補上後補完就寫不回宣告內。鎖定是語彙層的契約，不隨環境變數變動。

判定只看鍵，不看品類「有沒有接上來源」——資料上根本沒有「接上」的標記，宣告了同名鍵就是選擇加入。

### 五、仍有品項的品類不能刪除

同一個家族的問題：`DeleteCategoryCommand` 不碰品項，品項會留下懸空的 `CategoryId`。決定是拒絕刪除，回 409 並附品項數。不連帶刪品項（個人收藏，不可逆）、不搬到「未分類」（那是一個不存在的品類）。前端不預判，收到 409 才顯示訊息——為一個低頻按鈕讓每次列表載入多一次 aggregation 不划算。

### 六、被否決的替代方案

**(a) `Key` 鎖死，改名只能刪一加一。** 成本最低，而且完全消除這類 bug。否決是因為它把「改名會丟資料」變成使用者必須自己知道的陷阱；但如果日後發現使用者幾乎從不改鍵（`Label` 就夠了），這個選項會重新變成最好的答案。

**(b) 引入穩定的 `FieldId`，`Key` 變成可改的名字。** 後端靠 `FieldId` 比對兩份 `fields[]` 找出「這是改名」，再遷移品項。否決理由有兩層：第一，它是為了讓 diff 演算法能運作而發明的識別碼，沒有任何其他消費者——Mongo 路徑、來源、網址、白名單全部仍用 `Key` 定址，`FieldId` 解決不了「鍵被字面定址」這個事實，只是把推斷意圖的工作從不可能變成可能；第二，意圖本來就該在命令裡表達，靠比對反推是把使用者已經知道的事情丟掉再猜回來。

**(c) 不用 transaction，靠操作順序自癒。** 兩種順序的失敗窗口都會透過 `b9bc142` 的過濾造成資料遺失：品項先搬、schema 沒改，表單把新鍵當未宣告濾掉；schema 先改、品項沒搬，就是今天的孤兒狀態。「選對順序就自癒」不成立。dev 與 production 都在 Atlas replica set 上，測試 fixture 加 `.WithReplicaSet()` 即可，基礎設施已到位。

**(d) 通用 `IUnitOfWork` 讓所有 repository 共用 ambient session。** 改名是全案第一個、也是目前唯一一個跨 collection 的寫入（刪除品類的檢查是讀後刪，不是跨 collection 寫）。為一個操作改動每個 repository 的 session 傳遞太貴；改用專用 port `ICategoryFieldRenamer` 由 Infrastructure 一次做完。第二個跨 collection 寫入出現時再升級。

**(e) 允許改名的來源是未宣告屬性，順便當作孤兒救援工具。** 改名是「對宣告的操作」，擴成「搬移任意屬性」會讓詞彙變糊。08-07 之前產生的孤兒值沒有任何「舊鍵 → 新鍵」紀錄，已決定接受遺失。

## 後果

- `ICategoryFieldRenamer` 是 Application 層第一個明確要求 transaction 的 port。它的介面只承諾「全做或全不做」，不暴露 session。
- 鎖定違規（改名或撤回來源欄位）回 **400** 並指向具體欄位——這是「請求本身不合法」；資料衝突（改名撞到未宣告屬性、刪除有品項的品類）回 **409** 並附品項數——這是「資料狀態不允許，狀態變了就會成功」。
- 改名回應帶 `movedItemCount`。這件事的整個起因就是「改了鍵但沒人告訴你資料去哪了」，搬移數是使用者唯一能確認「真的動到資料」的證據。
- 網址與返回點裡的舊鍵（ADR-0010）在改名後變成不命中的篩選，不做遷移。改名不是高頻操作，使用者重選一次即可。
- `Category.Fields` 整包置換的 `PUT` 現在必須先讀取既有品類、比對鎖定集合，不再是純粹的覆寫。
- 未宣告屬性會累積。目前沒有清理工具，也沒有任何地方會讀它；若日後需要，「列出所有未宣告鍵與品項數」是一支 aggregation 就能回答的診斷查詢。
