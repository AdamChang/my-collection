# ADR-0014：邀請制——只由維運指令發出、綁定 email、邀請碼存明文

- 狀態：已接受
- 日期：2026-09-28
- 相關：tech debt I2（開放註冊）、I1（認證端點沒有速率限制）；open question Q12（使用者規模：未來改為邀請制）

## 背景

`/auth/register` 完全開放，任何人都能取得帳號，進而使用 `/ingest/fetch`（R4，SSRF）與上傳（M3）。Q12 已確認系統要改為邀請制。`User` 沒有角色欄位，系統內沒有「管理者」的概念，唯一會發邀請的人是系統維運者本人。

## 決定

### 一、邀請只能由維運指令發出，系統內沒有管理者角色

邀請的建立、撤銷、列出只提供 `maintenance invite create|revoke|list`（沿用 M2 的 `dotnet run --project src/MyCollection.Api -- maintenance …` 形式），Web 與 API 都沒有發邀請的入口。

不引入 `User.Role` 或管理者 email 清單。理由是：發邀請的頻率很低，只有維運者一人會做；多一個管理端點，就多一個要做授權、要防提權的攻擊面，而這次改動的目的正是縮小攻擊面。

開發環境同樣沒有「開放註冊」的開關。全新的資料庫（本機開發、還原演練、Atlas 重建）要建立第一個帳號，也是先用指令產生邀請。不用「沒有任何使用者時就允許註冊」的 bootstrap 規則，因為正式環境的資料庫一旦被清空、還原完成前，任何人都能搶先註冊成為第一人。

**結論翻轉的條件**：需要在行動裝置上隨手發邀請，或者讓使用者也能邀請他人。屆時必須引入角色，並補上授權 policy。

### 二、邀請綁定 email，一次性，7 天過期

註冊時的 email 必須和邀請上的 email 相同，碼外流也不能被別人使用。邀請用過一次即失效；建立時可用 `--days` 指定期限，預設 7 天；未使用前可以撤銷。同一個 email 同時只能有一份有效邀請：新發一份時，舊的未使用邀請會自動撤銷。已註冊的 email 不能再發邀請。

兌換邀請和建立帳號在同一個 MongoDB transaction 裡完成，由一個專責的 Infrastructure 類別負責，沿用 ADR-0012 `MongoCategoryFieldRenamer` 的模式，不做通用的 UnitOfWork。transaction 內依序執行：用條件更新消耗邀請（`Pending ∧ 未過期 ∧ email 相符 → Used`），再插入 User，最後回寫 `usedByUserId`。兩人同時用同一份邀請搶註，只有一人會成功；任何一步失敗都整筆回滾，邀請不會白白用掉，也不會留下沒有經過邀請的帳號。

被否決的做法有兩種。一是不用 transaction、先消耗再建帳號：建帳號失敗時邀請就用掉了，而且消耗當下拿不到 User 的 id。二是先建帳號再消耗：消耗失敗時會留下沒有經過邀請的帳號，等於繞過邀請制。

註冊失敗時，所有原因（碼不存在、已過期、已使用、已撤銷、email 不符）都回同一個訊息，真實原因只記在伺服器 log。

### 三、邀請碼存明文

這和 refresh token 只存雜湊的做法不一致，是刻意的：存明文，`list` 才能重新顯示碼，維運者不必在碼遺失時撤銷重發。

代價是：資料庫或 mongodump 備份一旦外流，外人會同時拿到碼和 email。由於系統不驗證 email 的所有權，對方可以直接用它註冊。曝險的範圍限於外流當下所有未使用、未過期的邀請；邀請是單次使用，而且預設 7 天過期，所以範圍很小，我們接受這個風險。

邀請碼使用 Crockford base32，約 100 bit，分組顯示成 `XXXXX-XXXXX-XXXXX-XXXXX`，比對時不分大小寫、忽略連字號。在 I1 還沒解決、`/auth/register` 沒有速率限制的前提下，碼的強度是防止暴力猜測的唯一防線。

**結論翻轉的條件**：備份的保管範圍擴大（例如 Q24 的 Google Drive 備份開放給他人存取），或者邀請的有效期限拉長到數週以上。這時應該改存雜湊。
