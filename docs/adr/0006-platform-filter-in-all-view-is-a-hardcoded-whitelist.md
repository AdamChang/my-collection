# 「全部」視圖的平台篩選是寫死白名單，不是通用跨品類機制

收藏頁要讓使用者在選「全部」（不選特定品類）時也能篩選平台，但 `platform` 是實體遊戲／數位遊戲兩個品類各自宣告的屬性，音樂專輯、電影光碟沒有這個欄位。既有的篩選列邏輯是「依目前選中的單一品類的 Fields 動態渲染」，選「全部」時找不到單一品類、故意不混用不同品類的 schema，所以目前完全不顯示任何屬性篩選。

我們只針對 `platform` 這個 key 開一個明確的例外：判斷邏輯是「有沒有品類宣告了這個 key」，不是「任何被兩個以上品類共用的欄位 Key，都自動在『全部』下出現」。後者看似更通用，但這個 Domain 目前沒有任何機制保證「不同品類的同名 Key 語意一致」——未來若兩個品類巧合宣告了同名但意義不同的欄位，通用機制會把它們誤判成可以混用篩選。窄的白名單換來的是可預期性：能跨品類出現的欄位是刻意加進來的，不是巧合命名的副作用。

## Consequences

- 前端判斷「這個品類支不支援平台篩選」用 `category.fields` 是否含 `key === 'platform'`，不是比對品類 ID；後端 `ListPlatformsAsync` 在「全部」（`categoryId` 為 null）時用 `Filter.Exists("attributes.platform")`，也不是硬編品類 ID 清單。兩邊都間接依賴 `AttributeValidator` 保證的不變式——非遊戲品類的品項不可能寫入 `platform` 這個 key。這個不變式若未來被打破，「全部」下的平台篩選會連帶跟著錯，屬於已知的耦合，不是意外。
- 之後如果想讓其他欄位也能跨品類篩選（例如某天新增的品類也想共用某個屬性），需要重新走一次這個決策、明確把該 key 加進白名單，而不會自動生效。這是刻意的，避免欄位命名巧合造成的隱性行為。
