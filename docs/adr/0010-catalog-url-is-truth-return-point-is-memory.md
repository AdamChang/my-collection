# ADR-0010：庫存頁的網址是真實來源，返回點是記憶

- 狀態：已接受
- 日期：2026-08-08
- 相關：[ADR-0006](0006-platform-filter-in-all-view-is-a-hardcoded-whitelist.md)（平台篩選的跨品類白名單）、[ADR-0009](0009-showcase-tabs-are-filters-not-layout-pickers.md)（精選頁 `?view=` 的既有慣例）

## 背景

庫存頁的篩選狀態原本只活在 `CatalogComponent` 裡。`/catalog` 是 lazy standalone route 且沒有 `RouteReuseStrategy`，離開即銷毀，所以使用者從列表點進某筆品項、編輯完回來，篩選一律歸零——瀏覽器上一頁也不例外。

需求是「回到列表時，回到的是同一個列表」。但回到列表有三條路徑，而它們能取得的資訊並不相同：

1. **瀏覽器上一頁**——history entry 裡有完整網址。
2. **導覽列的「庫存」**——`app.ts` 裡寫死的 `/catalog`，不帶任何資訊。
3. **item-detail 上新增的「← 返回列表」按鈕**——這個頁面完全不知道使用者是從哪一組篩選點進來的，甚至不知道他是不是從列表點進來的（可能是「新增品項」，也可能是直接貼網址）。

只靠一種機制無法同時滿足這三條。

## 決定

### 一、篩選條件的唯一真實來源是網址

`search`、`categoryId`、`attr.<key>`、`missingAttrs`、`tags` 全部進 `/catalog` 的 query param，參數名與 `ItemEndpoints` 解析的那一套同名。

這不是新發明的做法，而是延續既有慣例：精選頁的頁籤狀態已經是 `?view=` query param，`showcase-view.ts` 的註解裡甚至已經在推理「書籤存了 `?view=hero`、之後那些品項都被取消精選會怎樣」。同一個 codebase 對「篩選狀態放哪」應該只有一個答案。

### 二、返回點是一份獨立的記憶，只回答「回去要去哪」

sessionStorage 存一份 `{查詢字串, 已載入頁數, 錨點品項 id}`，每次篩選變更即覆寫。導覽列的「庫存」連結與 item-detail 的「返回列表」按鈕都從它組出目的地。

兩者職責明確切開，不重疊：

- **網址**回答「這個列表現在包含哪些品項」——它是列表的**身分**。
- **返回點**回答「使用者上次離開時在哪」——它是**瀏覽進度**。

「已載入 N 頁」與「錨點品項」因此刻意**不進網址**：它們是進度不是身分。附帶好處是避開一個語意陷阱——`?page=3` 在這裡是「載入第 1..3 頁」，與一般分頁「第 3 頁」的讀法不同，放進一個可貼可改的網址等於埋一顆地雷。

還原時必須先比對記憶裡的查詢字串與當前網址是否一致，不一致就只還原第一頁、不捲動。否則使用者手改網址換了篩選，卻套用上一組篩選的頁數與錨點。

### 三、被否決的替代方案

**(a) 純網址，不做記憶。** 這是最直覺的 Angular 做法，也正因為直覺，未來讀者一定會問「為什麼不乾脆全塞 URL」。否決理由是它解不了上述路徑 2 與 3：導覽列連結與返回按鈕都沒有辦法憑空知道該帶哪些參數。退一步說「那就只支援瀏覽器上一頁」也不行——存檔後 `item-detail` 會 `navigate(['/items', saved.id])` 多推一筆 history，上一頁的行為會變得不可預期。

**(b) 純 sessionStorage，不動網址。** 三條路徑確實能被一致處理，但代價是網址列對列表內容說謊：畫面上是 12 件篩選結果，網址是乾淨的 `/catalog`，F5 之後兩者才對得起來。而且它會讓這個 repo 對同一類問題出現兩套答案——精選頁在網址、庫存頁在儲存體——之後每加一個篩選都要先決定站哪一邊。

**兩者都被否決的共同理由**是它們都想用一個機制回答兩個不同的問題。分工之後，每一邊都變得容易解釋：網址可讀、可保存、可手改；記憶可以裝那些不該進網址的東西。

### 四、真實的取捨

分工不是免費的。承認的代價：

- **兩處狀態要保持一致**，而不一致是可能的（使用者手改網址）。這靠「查詢字串比對」這條規則收斂——它是整個機制中唯一會默默給出錯誤結果的分支，因此規格把它列為測試重點。
- **網址可貼可改，但不是被設計過的分享功能**：收件者需要自己的登入，看到的是自己的收藏。
- **記憶隨分頁消滅**。刻意不用 localStorage：隔天打開看到一個空蕩蕩的列表、卻不記得自己設過篩選，是很難自我診斷的困惑，而它省下的只是一次點選。

## 後果

- 導覽列的「庫存」連結不再是靜態 `routerLink="/catalog"`，必須從返回點組出目的地。它與「返回列表」按鈕必須行為一致——若一個記得、一個忘記，會比兩個都忘記更糟，因為使用者無法預期哪一條是安全的路。
- 篩選一旦跨頁存活，就會出現「我打開庫存，東西怎麼這麼少」。因此「清除全部篩選」是這個決定的**必要配套**，不是附加的便利功能。而因為記憶是在每次篩選變更時覆寫（不是離開時），清除不需要任何額外的清記憶邏輯——清除本身就會把記憶覆寫成無篩選。
- 未來要做具名檢視（Saved Views），可以直接建立在「一個查詢字串就是一組篩選」這個結論上，儲存的東西就是網址的 query string。這次的分工不會擋路。
- 精選頁維持現狀。若日後也要返回點，記憶必須先泛化成「每條路由一份」，屆時要決定 key 的命名與清除策略——現在刻意不提早付這筆設計成本。
- 後端零異動。所有參數與 `pageSize` 上限 200（`ItemQueries` 的驗證與 `MongoItemRepository` 的 clamp）都已足夠，還原上限因此定在 8 頁。
