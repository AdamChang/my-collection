# 補完端點有兩種回應語意，依來源而定

補完端點對 IGDB 是同步的——回應時作業已經結束，統計數字有意義；對 Steam 商店是非同步的——回應時作業才剛排進背景佇列，統計數字全是 0，進度要靠作業清單輪詢。差異源自兩個來源的成本：IGDB 可批次且允許每秒四次，Steam 商店逐款查且每五分鐘只有兩百次，數百款遊戲要跑十幾分鐘，綁在 HTTP 請求上必定逾時。

由來源自行宣告「是否偏好背景執行」，呼叫端不選擇。

## Consequences

- 前端必須依作業狀態決定要說「補完完成：更新 N」還是「已排入背景作業」。報前者會讓使用者以為沒東西可補。
- 這個不一致是刻意接受的，不是疏漏。把 IGDB 也改成非同步會超出本次範圍，且會讓一個本來能立即回報結果的操作變得更難用。**列為待清理**——若之後再加入第三個來源，應該先統一。
- 背景佇列是行程內的：重啟會丟掉尚未執行的項目，作業會停留在進行中狀態。使用者重按一次即可，代價低於引入外部佇列。
